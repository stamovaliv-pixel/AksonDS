# «Аксон ДокСлот» — комплект безопасности v4.1

Статическое веб-приложение записи поставщиков на слоты РЦ, использующее Supabase.

## Единственная SQL-миграция в этом комплекте

Используйте **только** [`supabase/security_hardening_v4_1.sql`](supabase/security_hardening_v4_1.sql). Это полный сценарий для установки security baseline и функций v4.1 в базе, где миграции v3/v4 ещё не выполнялись.

В этой папке намеренно оставлен один основной SQL-файл, чтобы не путать его с промежуточными версиями и инкрементальным патчем из предыдущих итераций.

## Установка

1. Создайте резервную копию базы PostgreSQL и отдельно сохраните объекты Storage.
2. Выполните предварительные проверки из [`SECURITY_README.md`](SECURITY_README.md).
3. Убедитесь, что выбран именно рабочий проект Supabase и структура соответствует проверкам.
4. Выполните [`supabase/security_hardening_v4_1.sql`](supabase/security_hardening_v4_1.sql) **один раз** в Supabase SQL Editor с правами владельца проекта. При ошибке остановитесь, сохраните текст ошибки и не запускайте SQL повторно без анализа.
5. Только после успешного завершения SQL опубликуйте файлы сайта из `AksonDS-main`, сохранив настройки хостинга, домен и конфигурационные файлы проекта.
6. Проверьте приёмочные сценарии для всех ролей, включая приватные реестры и исключённые даты.

Перед публикацией проверьте `js/supabase-client.js`: допустим только публичный ключ Supabase (`anon`/publishable key). Никогда не помещайте `service_role` или пароль БД в клиентский код.

## Включённые возможности

- безопасный вывод пользовательских данных и проверка ролей внутренних страниц;
- ограничение чтения данных поставщиками и серверная проверка бронирований;
- приватный bucket `registries` и временные signed URLs;
- изменение реестра до конца дня приезда согласно роли и владельцу записи;
- освобождение ворот после сохранения времени убытия;
- временный показ пароля на странице авторизации;
- календарь-модалка для выбора нескольких дат-исключений, закрытых для новых бронирований;
- проверка исключённых дат в PostgreSQL и очистка прошедших дат в часовом поясе `Asia/Almaty`.

## Ограничения и предупреждения

- SQL подготовлен по предоставленным результатам диагностики, но не выполнялся на вашей рабочей базе из этого архива.
- Миграция меняет RLS-политики пяти таблиц и правила Storage, переводит `registries` в приватный режим и обновляет функции/триггеры. Выполняйте её только после резервной копии.
- При переводе bucket в private ранее скачанные файлы и копии по старым публичным URL не отзываются у людей, которые уже их получили. После миграции проверьте старые URL и выдачу signed URLs.
- Для почасовой автоматической очистки дат-исключений включите `pg_cron` в Supabase. Если он недоступен, проверяйте уведомления SQL и обеспечьте очистку согласно `V4_1_DEPLOYMENT_README_RU.md`.
- Не запускайте SQL-файл поверх уже частично выполненной миграции без проверки текущего состояния базы.
