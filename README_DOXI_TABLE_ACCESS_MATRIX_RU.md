# Матрица доступа Докси к таблицам — инструкция

## Что добавлено

На странице `app/ai_ds_management.html` появилась секция «Матрица доступа Докси к таблицам». Управление секцией доступно только роли `super_admin`.

В матрице отображаются все 25 таблиц из текущего списка Supabase:

- `admin_personal_notes`
- `admin_personal_reminders`
- `app_notifications`
- `app_settings`
- `audit_log`
- `booking_verification`
- `bookings`
- `contacts`
- `doxi_action_audit`
- `doxi_action_drafts`
- `doxi_conversations`
- `doxi_knowledge_documents`
- `doxi_messages`
- `doxi_notes`
- `doxi_reminders`
- `doxi_settings`
- `doxi_thinking_comments`
- `doxi_user_memory`
- `load_advisory_settings`
- `load_advisory_signal`
- `load_control_audit_legacy`
- `notification_preferences`
- `profiles`
- `push_subscriptions`
- `shift_board_settings`

Для каждой таблицы предусмотрены разрешения `SELECT`, `INSERT`, `UPDATE`, `DELETE`, область строк и лимит строк в запросе.

## Важная модель безопасности

Матрица не даёт языковой модели произвольный SQL и не выполняет автоматический CRUD для любой таблицы. Запись разрешается только через существующие серверные сценарии с валидацией. Если для операции нет отдельного безопасного обработчика, соответствующий переключатель заблокирован и сервер отклонит попытку включить его через API.

Особые правила:

- `profiles`: только `SELECT`. Запись, изменение и удаление заблокированы на сервере и ограничены SQL constraint.
- `push_subscriptions`: полностью закрыта, поскольку содержит push-ключи и токены.
- `doxi_action_drafts`: внутренний механизм подтверждений, недоступен как обычная таблица чата.
- `doxi_settings`: конфигурация управляется отдельной защищённой страницей Super Admin и не раскрывается чату через матрицу.
- `bookings`: чтение доступно `admin` и `super_admin`; запись/изменение/удаление доступны только при одновременном разрешении матрицы и соответствующего переключателя полномочий Докси. Действия с записью требуют существующего подтверждения.
- Личные заметки, напоминания, память, диалоги и пользовательские предпочтения по умолчанию ограничены строками текущего пользователя. Для роли `admin` это ограничение жёсткое и сохраняется даже если в матрице выбрано «Все строки»; Super Admin может использовать установленную в матрице область.

Матрица является глобальной для Докси, а не отдельной настройкой по каждой роли. При этом подробное чтение таблиц `bookings` и выбранных таблиц через контекст доступно только `admin` и `super_admin` и только при включённом общем переключателе «Чтение актуальных данных». Сама страница управления матрицей и API её изменения доступны только `super_admin`.

## Установка

1. Сделайте резервную копию проекта и базы данных.
2. Откройте Supabase → SQL Editor.
3. Выполните целиком миграцию `supabase/migrations/20261116_doxi_table_access_matrix.sql`.
4. Опубликуйте Edge Function:

   ```bash
   supabase functions deploy doxi-chat
   ```

5. Опубликуйте фронтенд-файлы из патча:
   - `app/ai_ds_management.html`
   - `js/ai-ds-management.js`
   - `css/ai-ds-management.css`
   - `supabase/functions/doxi-chat/index.ts`
6. Войдите под `super_admin` и откройте страницу управления Докси.
7. Убедитесь, что отображаются 25 таблиц. Проверьте начальные разрешения и сохраните изменения.

SQL миграцию нужно выполнить до публикации новой Edge Function. Если миграция не применена, сервер закрывает доступ к таблицам по принципу fail closed, а интерфейс покажет ошибку загрузки матрицы.

## Начальные разрешения

- `bookings`: SELECT включён, запись/изменение/удаление выключены.
- `profiles`: SELECT включён, все изменения запрещены.
- `admin_personal_notes` и `admin_personal_reminders`: CRUD включён через существующие личные сценарии, область — текущий пользователь.
- `doxi_user_memory`: CRUD включён через штатные API личной памяти, область — текущий пользователь.
- `doxi_knowledge_documents`: SELECT/INSERT/DELETE включены через защищённое управление базой знаний.
- `doxi_thinking_comments`: CRUD включён через серверный интерфейс управления комментариями.
- `push_subscriptions`, `doxi_action_drafts`, `doxi_settings`: закрыты для чтения/изменения из чата.
- Остальные таблицы по умолчанию закрыты; Super Admin может включить SELECT там, где это не запрещено жёсткими правилами.

## Как трактовать столбцы

- **Чтение** — разрешить серверу передавать выбранные строки в контекст Докси.
- **Добавление / Изменение / Удаление** — разрешить только соответствующий существующий серверный сценарий. Эти переключатели не создают универсальную операцию над таблицей.
- **Область строк** — `Все строки` или `Текущий пользователь`, если у таблицы есть безопасный идентификатор владельца (`admin_id` / `user_id`).
- **Лимит** — верхний предел строк для одного контекстного/календарного чтения (1–1000). Отдельные карточки и подтверждающие сценарии имеют более строгие собственные лимиты.

## Проверка после публикации

1. Под `super_admin`: открыть матрицу, отключить SELECT у `bookings`, сохранить; запрос Докси о количестве записей должен сообщить, что чтение запрещено. Затем вернуть SELECT.
2. Под `admin`: Докси должна читать записи, если роль разрешена в общих настройках доступа.
3. Под `operator`/`supplier`/`viewer`: контекст полного чтения таблиц не должен передаваться.
4. Попытка включить `UPDATE` или `DELETE` для `profiles` должна отклоняться сервером; checkbox заблокирован.
5. Попытка включить любое право для `push_subscriptions` должна отклоняться сервером; все checkbox заблокированы.
6. Для `bookings` включение INSERT/UPDATE/DELETE в матрице недостаточно само по себе: соответствующее полномочие должно быть включено в основных настройках Докси, а подтверждение действия остаётся обязательным.

## Что проверено локально

В этой сборке выполнены статические проверки JavaScript/TypeScript, соответствия 25 таблиц в каталоге, SQL allow-list и seed-значениях, наличия серверной проверки ролей, блокировок `profiles`/`push_subscriptions` и подключения UI к API матрицы. Production Supabase и реальные данные проекта не подключались; после публикации обязательны приёмочные проверки выше.
