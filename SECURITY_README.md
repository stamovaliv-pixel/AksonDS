# «Аксон ДокСлот» v4.1 — проверка и установка безопасности

## Какой SQL запускать

В комплекте есть **один основной SQL-файл**: `supabase/security_hardening_v4_1.sql`.

По данным пользователя, миграции v3/v4 ещё не применялись. Поэтому нужен полный SQL v4.1 — не старый `security_hardening.sql` и не инкрементальный патч `security_patch_v4_registry_gates.sql`. Эти промежуточные файлы из итогового архива удалены, чтобы исключить ошибочный выбор.

## Перед миграцией

1. Создайте резервную копию PostgreSQL и убедитесь, что она пригодна для восстановления. Отдельно скачайте объекты bucket `registries`: SQL-дамп не содержит физические файлы Storage.
2. Проверьте, что выбран рабочий проект Supabase.
3. Сверьте таблицы и основные поля:
   - `profiles(id, company_name, inn, role, is_blocked, created_at)`;
   - `bookings(id, profile_id, slot_date, slot_hour, supply_type, supply_types, order_type, order_number, registry_file_url, is_tk, comment, status, gate_number, arrival_time, departure_time)`;
   - `contacts(id, profile_id, full_name, phone, is_primary)`;
   - `app_settings(id, slot_start_hour, slot_end_hour, slots_per_hour, reserve_slots_per_hour, booking_deadline_hours, return_deadline_days, available_days, supply_types, registry_template_url)`;
   - `audit_log` с фактическими полями проекта.
4. По результатам предварительной проверки на всех пяти таблицах включён RLS. Повторно проверьте, что не появились новые политики или триггеры после снимка.
5. В исходной базе были подтверждены триггеры `on_auth_user_created`, `trg_check_slot_capacity`, `trg_check_user_limit`. Миграция v4.1 обновляет серверную логику бронирования и `handle_new_user`; убедитесь, что не добавлены другие пользовательские триггеры с дублирующей логикой.
6. В исходном Storage bucket `registries` был публичным, а политики назывались `Allow public read` и `Allow authenticated uploads`. Полный SQL v4.1 закрывает публичный доступ и устанавливает правила для приватного bucket. Если после проверки создавались другие политики, повторно проверьте их до миграции.
7. Предварительная проверка сопоставила сохранённые ссылки реестров с объектами Storage. Несмотря на это, убедитесь, что резервная копия включает все объекты и контрольные суммы.
8. Обеспечьте короткое окно обслуживания: во время миграции пользователи не должны создавать или изменять бронирования.

## Применение

1. Включите `pg_cron` в Supabase Dashboard, если планируется автоматическая почасовая очистка прошедших дат-исключений.
2. Откройте Supabase SQL Editor и выполните **один раз** `supabase/security_hardening_v4_1.sql`.
3. Если SQL завершился ошибкой, не публикуйте обновлённый фронтенд и не запускайте тот же скрипт вслепую. Сохраните ошибку и проверьте фактическое состояние базы.
4. После успешного `COMMIT` опубликуйте файлы сайта из архива v4.1.

## Что меняет миграция

- политики RLS таблиц `profiles`, `bookings`, `contacts`, `app_settings`, `audit_log`;
- права SQL и функции проверки роли/блокировки пользователя;
- регистрацию: создаются профиль поставщика и основной контакт;
- серверную проверку бронирования, вместимости, пользовательского лимита и занятости ворот;
- приватный режим bucket `registries`, его Storage-политики и формирование подписанных ссылок;
- возможность менять реестр до конца календарного дня приезда для уполномоченных ролей;
- `app_settings.booking_excluded_dates` и серверный запрет новых активных бронирований на исключённых датах;
- функцию очистки прошедших исключений по часовому поясу `Asia/Almaty`; при наличии `pg_cron` создаётся почасовая задача.

## После миграции — приёмочные проверки

- Вход и доступность страниц для `supplier`, `operator`, `admin`, `viewer`.
- Поставщик не может читать или изменять чужие бронирования или менять собственную роль/блокировку.
- Администратор может задавать несколько исключённых дат в календаре настроек; поставщик не может изменять эти настройки.
- Создание активной записи на исключённую дату отклоняется базой даже при прямом запросе API.
- Прошедшая дата очищается задачей Cron либо серверной очисткой при открытии настроек.
- Реестры скачиваются через подписанные ссылки; прежний публичный URL больше не предоставляет публичный доступ.
- Замена реестра разрешена до конца дня приезда согласно роли, а после даты приезда отклоняется.
- Ворота можно назначить следующей поставке после заполнения времени убытия; параллельные назначения не создают конфликтов.
- Действующие записи и профильные данные остаются на месте.

## Важные оговорки

SQL подготовлен по предоставленным диагностическим результатам, но **не был выполнен на вашей рабочей базе**. Поэтому требуется резервная копия и фактическая проверка после применения. Перевод Storage в приватный режим не удаляет ранее скачанные пользователями копии файлов и не отзывает их копии вне Supabase. В диагностике обнаружен один профиль без контакта; миграция не должна создавать фиктивные контактные данные — исправьте их отдельно через штатный процесс.
