# AKSon DockSlot v4.1 — установка исключённых дат

## Что добавлено

1. Администратор выбирает несколько дат исключений в календаре-модалке на странице `app/settings.html`.
2. Новые активные бронирования на эти даты блокируются на стороне PostgreSQL, независимо от дня недели. Сервер также запрещает перевод отменённой записи обратно в active и перенос активной записи на закрытую дату. Существующие записи могут оставаться доступными для операционных изменений, если дата не меняется.
3. Прошедшие даты удаляются из массива `app_settings.booking_excluded_dates` функцией `public.cleanup_expired_booking_excluded_dates()` в часовом поясе `Asia/Almaty`. В v4.1 SQL пытается настроить почасовой cron при наличии `pg_cron`; страница настроек также выполняет очистку при открытии администратором.
4. На календаре поставщика исключённые даты отображаются закрытыми, а на странице дня новые записи недоступны. Уже существующая собственная запись на такой день остаётся открываемой для просмотра.

## Установка в рабочей базе

1. Сделайте полную резервную копию PostgreSQL и отдельных объектов Storage до миграции.
2. В Supabase Dashboard включите `pg_cron`: Integrations → Cron → Enable, если расширение ещё не включено.
3. Проверьте, что выбран рабочий проект и таблицы соответствуют `SECURITY_README.md`.
4. До запуска SQL в Supabase Dashboard → Storage → `registries` отключите `Public bucket` (сделайте bucket Private). Это необходимо, потому что Supabase управляет таблицей `storage.objects`; миграция проверяет приватность и RLS, но не выполняет `ALTER TABLE storage.objects` и не меняет настройки bucket SQL-командой.
5. В SQL Editor выполните **один раз** полный `supabase/security_hardening_v4_1.sql` из этого комплекта. Он включает весь security baseline v4 и новое поле исключений. Не запускайте поверх него старые v3/v4 SQL и отдельный patch.
6. После успешного `COMMIT` опубликуйте файлы сайта из `AksonDS-main` в GitHub/хостинг. Не перезаписывайте настройки хостинга/CNAME секретами.
7. Проверьте дату-исключение на тестовом дне: поставщик не должен суметь создать запись через интерфейс или прямой PostgREST insert. Удалите исключение и убедитесь, что обычная запись снова доступна.
8. Проверьте cron job: `select jobid, jobname, schedule, command from cron.job where jobname = 'akson-clean-expired-booking-excluded-dates';` и историю запуска в Supabase Dashboard → Cron.

## Важно

- SQL не запускался на рабочей базе; его нужно выполнять после резервной копии.
- Если `pg_cron` отсутствует, SQL не аварийно прекращает миграцию: он выдаёт NOTICE. В этом случае включите Cron в Dashboard и повторно зарегистрируйте job согласно `supabase/security_hardening_v4_1.sql`/`SECURITY_DEPLOYMENT_NOTES.md`.
- В интерфейсе доступна только роль `admin`; серверная проверка является обязательной защитой. RLS на `app_settings` также должен оставаться admin-only для UPDATE.
- Таймзона всех сроков исключения — `Asia/Almaty`. Задача работает ежечасно, поэтому просроченная дата удаляется в ближайший час после перехода даты; при открытии настроек администратором очистка выполняется сразу.
